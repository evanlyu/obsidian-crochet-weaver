## Context

`RenderItem` (`src/types.ts`) currently carries only `{ symbol, x, y, rotation, loop? }` — no link back to which AST row/unit produced it. `roundStitchCount`/`outputStitches` (`src/layout/steps.ts`) already compute a *weighted* stitch count per row (`inc` = 2, everything else = 1, groups sum their flattened children), which is what the stitch counter's "X / Y stitches" already displays — but that weighting doesn't correspond 1:1 with render items (one `inc` is one rendered symbol worth 2 stitches). `renderCrochetTool` (`src/tool.ts`) already computes, on every `paint()`, the current row and `stitchDone` (see `add-stitch-counter`); this is exactly the data needed to point at a chart position, it's just never communicated outside the panel.

## Goals / Non-Goals

**Goals:**
- Tag every `RenderItem` with the row and "unit" (unrolled stitch-or-group step, matching `unroll()`'s granularity) it came from, so a `(rowIndex, unitIndex)` pair can be resolved to concrete chart symbols.
- The stitch counter tracks whole units directly (`unitsDone`, see the `add-stitch-counter` fast-follow fix), so the highlight target's `unitIndex` is simply `unitsDone` — no separate weighted-to-unit lookup needed; a crocheter thinks in terms of "which symbol am I working," not raw weighted counts, so an `inc` (2 output stitches, 1 symbol) is one indivisible highlight target.
- Live-update the chart highlight as the paired embedded tool's state changes, entirely client-side (no persistence needed for the highlight itself — it's derived from progress state that's already persisted).
- One color setting drives both a subtle "current row" wash and a stronger "current stitch" highlight, so the two behaviors the user described (whole-row wash from the row list, precise stitch pointer from the counter) coexist instead of needing a precedence switch — the stitch pointer is simply drawn more strongly than the row wash it's already part of.

**Non-Goals:**
- No cross-block sync (a standalone `crochet` chart and a separate standalone `crochet-tool` block, even sharing an `id`, will not highlight each other in this change) — only the embedded (`tool: on`) case, where chart and tool already share one render call, gets live highlighting.
- No highlighting for `crochet-pattern-text` (no progress state) or standalone `crochet-tool` (no paired chart).
- No frontmatter override for the marker color (matches `showNextRoundMarker`'s precedent of being global-only).

## Decisions

- **`RenderItem` gains optional `rowIndex?: number` and `unitIndex?: number`.** Populated in `layout/round.ts`, `layout/spiral.ts`, `layout/flat.ts` at the same point each item is already created (including every child item of a fanned-out group, which all share the same `unitIndex` — highlighting a group highlights the whole cluster, matching how a crocheter treats "make this cluster" as one action). The center-anchor items from `pushCenterAnchor` and the next-round marker are left untagged (`undefined`) since they don't belong to a specific row/unit.
- **`unitIndex` is the index into `unroll(row.steps)` after popping a trailing join `sl st`, exactly mirroring `roundStitchCount`'s own popping rule.** This keeps a single source of truth for "how many units/stitches does this row have" between the count shown in the panel and the index space used for highlighting. Popping only ever removes the last element, so indices below the popped length mean the same unit in both the popped and un-popped views — safe even for `layoutSpiral`/`layoutFlat`, which don't pop a trailing join themselves (an existing, unrelated inconsistency, not something this change fixes).
- **`unitStitchCounts(row)` in `layout/steps.ts`** returns one weight per unit (popped join excluded, same list `roundStitchCount` sums) — used by the stitch counter to advance by a whole unit per tap, and no longer needed for highlight resolution once the counter tracks units directly (see below).
- **`renderCrochetTool` gains an optional 5th parameter `onHighlightChange?: (target: ChartHighlight | undefined) => void`,** called at the end of every `paint()` with `{ rowIndex, unitIndex: unitsDone }` for the current row/target stitch, or `undefined` once the pattern is complete. This keeps `tool.ts` decoupled from rendering — it just reports state, same shape it already computes for its own UI.
- **`main.ts`'s embedded `tool: on` path re-renders the chart on every highlight change** by keeping a reference to the chart container and calling `renderSVG` again (clearing the container first) with the new highlight target, instead of trying to mutate specific SVG nodes in place. `renderSVG` is cheap (chart sizes are budget-limited) and this avoids a second, more fragile "patch an existing SVG" code path.
- **Rendering: recolor the symbol itself, not a background circle.** An earlier version of this change drew a filled background circle behind highlighted items; the user found the circled/haloed look too visually busy. Revised to match the existing `highlightIncDec`/`.crochet-weaver-accent` pattern instead: `render.ts` adds `.crochet-weaver-row-highlight` (CSS `opacity: 0.55`) or, for the target unit, `.crochet-weaver-stitch-highlight` (`opacity: 1`) directly to the item's `<use>` element, and sets `use.style.color` to `RenderOptions.chartMarkerColor` inline so the symbol's own `currentColor` strokes/fills pick it up — no extra shape drawn. Default `chartMarkerColor` is a yellow (`#e6a700`), chosen to read clearly against both light/dark chart backgrounds and stay visually distinct from `nextRoundMarkerColor`'s orange and the `highlightIncDec` accent color.

## Risks / Trade-offs

- [Threading `rowIndex`/`unitIndex` through three layout modules touches code that's otherwise stable] → Mitigation: purely additive optional fields; existing layout tests only assert on `symbol`/`x`/`y`/`rotation` and are unaffected.
- [Re-rendering the whole SVG on every tap is more work than patching one node] → Mitigation: chart item counts are budget-capped; this matches the existing pattern of `renderCrochetTool` fully re-rendering its own DOM (`root.empty()` + rebuild) on every interaction.
- [No cross-block sync may surprise users who split chart and tool into separate blocks] → Mitigation: explicitly called out as a non-goal; can be proposed separately if requested.
