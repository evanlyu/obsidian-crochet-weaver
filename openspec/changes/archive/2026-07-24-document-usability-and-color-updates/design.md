## Context

This batch touches three previously-independent layers of the plugin: the layout engine (`src/layout/*`, pure geometry, no DOM), the renderer (`src/render.ts`, builds the SVG), and the progress-tool UI (`src/tool.ts` + `styles.css`, DOM/CSS only). The color-change feature threads new state through all three; the usability fixes are mostly isolated to render/CSS but two of them (grid-guide anchoring, mesh drift) are layout-level.

## Goals / Non-Goals

**Goals:**
- Let a color-change instruction ("8 sc BLACK, change to WHITE, 8 sc WHITE, ...") be represented directly in pattern text and be visible on the chart, without turning the chart into a literal-color rendering that fights the Obsidian light/dark theme.
- Make chart and tool-panel overflow (on narrow/portrait widths, or on many-round charts) *degrade gracefully* — scroll/wrap — instead of clipping content or squeezing everything illegibly small.
- Keep every fix additive: no existing pattern's rendered output, parsed AST shape, or persisted progress data changes unless that pattern now uses one of the new features.

**Non-Goals:**
- No color *palette* or named-swatch system — `color` accepts any CSS color name or `#hex` verbatim; the plugin does not validate, normalize, or theme-adapt it.
- No attempt to make literal yarn colors (e.g. `black` in a dark theme) automatically legible — that would misrepresent the actual color. The chart symbols themselves therefore never adopt the yarn color; only the small ring marker does, and it's given its own explicit color rather than relying on `currentColor`.
- No redesign of the settings-tab architecture — the AI-doc copy buttons use the existing `SettingDefinitionRender` escape hatch (Obsidian 1.13+) plus a manual `display()` fallback, matching how every other setting in this tab is already dual-implemented.

## Decisions

- **Color state threads through `unroll()` via a mutable `ColorState` ref (`{ current?: string }`), not a parallel return value.** A `ColorChangeNode` step is consumed (sets `colorState.current`) rather than becoming a render unit; every `StitchNode`/`GroupNode` unit `unroll()` produces afterward is tagged with `.color` from the shared ref. Callers that don't care about color (`flattenGroup`, `poppedUnits`/count helpers) simply omit the second argument and get a fresh, throwaway state — fully backward compatible. Callers that need cross-row persistence (`flat.ts`, `round.ts`, `spiral.ts`) pass one `ColorState` object across their whole `rows.forEach` loop, since yarn color persists between rounds until explicitly changed, matching real crochet.
  - Alternative considered: return `{ units, colors }` parallel arrays from `unroll()`. Rejected — it would force every existing call site (including `flattenGroup`'s recursive self-calls) to change shape for a feature most of them don't need.
- **Color markers are a separate `ColorMarker[]` list on `LayoutResult`, not a boolean flag on `RenderItem`.** Each layout function tracks `previousColor` while placing items and appends a marker `{x, y, color}` the first time a unit's color differs from the previous one. `normalize()` treats markers like `gridGuide` circles: included in the bounding-box pass, shifted by the same `dx`/`dy` as everything else, collapsed to `undefined` when empty (not `[]`) to match the sparse-field convention already used by `rowConnectors`/`gridGuide`.
- **The chart never repaints stitch symbols in the yarn color; only a small hollow ring marks the first stitch of a new color.** First implementation *did* recolor stitch symbols via inline `style="color: ..."` (reusing the existing current-position-highlight mechanism) and drew the marker as a filled dot behind the symbol. User feedback against the real rendered chart identified two problems: a filled dot hid the stitch symbol it was flagging, and literal colors (especially `black`) on symbol strokes went illegible against a dark theme while also visually competing with the progress tool's own gold current-position highlight. Final design: symbols always stay `currentColor` (theme-default); the marker is `fill: none` with `stroke: <yarn color>`, radius tuned down from an initial 11px/2x-stroke to 8px/1.3x-stroke after another round of visual feedback.
- **Progress-tool rows use CSS Grid (`grid-template-columns: auto minmax(0, 1fr) auto`), not flex.** The row (badge / pattern-text / stitch-count) went through three iterations: (1) flex with no wrap handling — long rows clipped off narrow screens; (2) flex with `min-width: 0` + `overflow-wrap` on the text column plus `flex-wrap: wrap` on the row — still overlapped, because the row is a `<button>` element and flex's per-item `min-width: auto` default has to be defeated at *every* ancestor in the chain (chart wrapper → panel → row → text), and even then the observed rendering (verified in an actual browser, not just reasoned about) showed the count column overlapping wrapped text rather than reflowing. Grid's `minmax(0, 1fr)` middle track sidesteps the whole class of bug: badge and count get fixed content-sized columns that can never overlap the middle column by construction, and the middle column's wrapped text simply grows the row's height. Verified this time by actually rendering the component (happy-dom → static HTML → Safari, screenshotted) rather than reasoning from the CSS spec alone, after two prior flex-based fixes both looked correct on paper and were not.
- **`overflow-wrap: break-word` + `word-break: normal`, not `overflow-wrap: anywhere`.** `anywhere` breaks at any character (including mid-word for stitch abbreviations) and also factors into min-content sizing, which was useful while fighting flex's auto-sizing but is unnecessary once the grid track is explicitly `minmax(0, ...)`. `break-word` only forces a break as a last resort, giving more natural wrapping for the mostly-CJK readable-mode text.
- **Readable-mode anchor formatting leads with the anchor and wraps the steps: `魔術環(短針6)`, not `短針6, 魔術環`.** First implementation trailed the anchor comma-separated (mirroring raw mode's `6 sc in MR`); user feedback against a real chart's tool panel asked for anchor-first with parens. `rowStepsText()` branches on `style === 'readable' && row.anchor` to build this form; raw mode is unchanged.
- **The AI-doc translations are embedded as generated TS string constants (`src/ai-doc-content.ts`), not loaded from `docs/*.md` at runtime.** Community plugin releases only ship `main.js`/`manifest.json`/`styles.css` — arbitrary repo files like `docs/*.md` never reach an installed user's vault. Bundling the text directly into the compiled plugin is the only way the copy-to-clipboard feature works for a real install, not just a dev checkout. The generator script (ad hoc, not committed) re-escapes the four `docs/ai-pattern-authoring*.md` files into one template-literal export; a test asserts byte-for-byte equality between the two so they cannot silently drift.

## Risks / Trade-offs

- [`docs/*.md` and `src/ai-doc-content.ts` can drift if someone edits one and forgets the other] → Mitigation: `tests/ai-doc-content.test.ts` fails the suite if they're not byte-identical.
- [Literal yarn colors can still be low-contrast against a user's theme, since the plugin does not adapt them] → Accepted trade-off, documented in the AI reference and README: this is definitionally correct behavior for representing a real yarn color, and the ring-marker + tool-panel text ("change to `<color>`") remain legible regardless.
- [CSS Grid row layout was reached after two visibly-wrong flex iterations shipped mid-session] → Mitigation: this change's own history is the cautionary example — the final verification step (render + screenshot a real browser) is now the standard for any further row-layout change to this component, not just CSS review by inspection.
